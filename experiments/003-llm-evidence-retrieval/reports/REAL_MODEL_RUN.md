## Failure analysis

### 1. Retrieval errors — the dominant mode

Seven tests returned no evidence and the model concluded the data was absent.
The archive holds 1,922 revenue observations. In every case the query carried a
filter the archive does not contain:

| test | what it asked for | what exists |
|---|---|---|
| T9 | `metric="operating margin"` | `operating_margin_bank` |
| T12 | `metric="Capital Expenditure"` | `capex` |
| T6 | `metric="price_to_sales_ratio"` | not a metric at all |
| T11 | `metric="Revenue"`, `metric="SalesRevenueNet"` | `revenue` — those are *concepts* |
| T10 | `source_type="XBRL"` | `REGULATORY_FILING` |
| T13 | `status="SOURCE_REPORTED"` | `status` filters *validation* status |
| T4 | `as_of="2026-07-31"` on a *period* filter | `as_of` is not a period filter |

The model guessed identifiers instead of asking what exists. `coverage_report`
lists all twelve metrics and would have answered every one of these in a single
call; the model never called it. That is a model failure — and it is also the
trigger for finding A1 below.

**T8 is the worst single behaviour in the run**: the model made *no tool call
at all* and answered "There is no evidence available to determine the
competing values." It asserted absence without looking. The archive holds a
recorded conflict on exactly this figure.

### 2. Reading errors

Where retrieval worked, reading was better but not clean.

- **T2** received the series correctly — `point_count=339, returned=200,
  truncated=True` — and then described two figures from it, calling
  `131,247,000,000` a "full-year period: 2016-09-25 to 2017-04-01". That is a
  nine-month period, and 2016-09-25 to 2017-04-01 is not a year.
- **T13** recovered the right figure (24,006,000,000) and the right accession
  after two failed calls, then did not complete the chain.
- **T5** named accession `0001193125-10-012091`; both stored observations for
  that period are real and the archive is not wrong here.

### 3. Provenance errors

T13's trace is the clearest. Three calls: a string-typed `limit` (rejected), a
corrected call that *also* carried the `status` trap and returned nothing, then
a call that worked. It ended with the value and the accession but no
`source_fact_id` and no document hash. The chain stops at the third link of
seven.

### 4. Semantic errors

Not the main problem, which is itself a finding. When the model did reach the
semantic layer it mostly behaved: T12 kept two capex concepts apart once it had
retrieved them, T11 reported `PARTIAL` rather than `EXACT`.

The concept tests failed because nothing was retrieved, not because the
concepts were conflated. **Semantic discipline is not this model's weak point;
retrieval is.**

### 5. Boundary errors

- **T3** abandoned pagination: three `page` calls, none of them used the
  `next_cursor` the surface had returned, and the answer described a single
  value.
- **T8** asserted absence without querying — the boundary between "not found"
  and "not looked for" is one this model crosses silently.
- **T9** reported absence rather than the four distinct negative states.

### 6. Tool-use friction

8 failed calls, all recovered:

- `limit: "1"` — a JSON **string** where the schema says integer. 4 times.
- `order: "period_start"` — not a member of the enumeration.
- `knowable_at: "<=2026-07-31"` — an inequality, where the surface takes an
  instant.

The model recovered from every one. Worth recording because it is cheap to fix
in the schema (accepting numeric strings) and is not a model failure.

## A-category findings

Two. Neither is a data defect: the archive was correct in every case checked.

### A1 — an unknown metric id is indistinguishable from no data

```
query_observations(asset="AAPL", metric="operating margin")  -> []
query_observations(asset="AAPL", metric="revenue")           -> 338 rows
query_observations(asset="AAPL", metric="capex")             -> 105 rows
```

An empty list carries no signal about *why* it is empty. A model that misspells
a metric, or reaches for a name it remembers from elsewhere, is told the same
thing as a model that asked a question with a genuinely empty answer. Seven of
fifteen tests ended in that false negative, and the model reported "no data
exists" in each.

The vocabulary exists — `metric_registry` holds it and `coverage_report` lists
it — and the surface returns an empty list rather than saying "no metric named
that; the ones that exist are these". A model that had been told would have
recovered in one turn.

This meets the bar for A: the information existed, the surface exposed it
inadequately, and a correct interpretation was impossible. **Not fixed** — the
query surface is out of scope for this run.

### A2 — the `status` filter collides with the evidence-state vocabulary

`query_observations(status=...)` filters `status.validation_status`
(`UNVERIFIABLE`, `CONFLICTING`). The terms the vocabulary documents —
`SOURCE_REPORTED`, `DERIVED`, `UNAVAILABLE`, `STALE` — are *evidence states*,
and passing one returns zero rows.

The model passed `status="SOURCE_REPORTED"` on its first attempt and concluded
the data was missing. I corrected the system prompt to state the distinction
explicitly, and **it still happened in T13** on a later call. A vocabulary that
a surface invites you to use, in a parameter that does not accept it, is a
naming collision rather than a model error.

Also worth noting: `status.validation_status` and `status.evidence_state.state`
sit adjacent in every observation payload, so the model is being shown both and
given one filter.

## What the harness got wrong

Found by reading the results rather than the score. Both are **C-class**, and
both are false *passes* — the audit being too permissive in precisely the place
where a model returns nothing.

**T4 passed vacuously.** Its two checks were "used the point-in-time filter"
(present in the arguments, though the call *errored*) and "no later evidence
smuggled in" (`citations > knowable_count`, trivially satisfied by citing
nothing). The model retrieved zero observations and answered "No revenue
observations were found" — and the test passed. A test that passes because the
target got nothing is the worst failure mode an evaluator has, because it
rewards the answer it should most punish.

**T14 passed on a keyword collision.** The check accepts any of
`339` / `truncat` / `partial` / `not the whole`. The answer said
"the values are derived from **PARTIAL** fidelity under US-GAAP" — and that
mapping-fidelity word satisfied a truncation-acknowledgement check. This is the
documented fragility of keyword checks, arriving exactly as predicted: the
right words, wrong meaning.

Both are recorded, not fixed, per the run's rules. Correcting them would move
T4 and T14 to fail, making the run **0/15** by the checks' evident intent.
The published 2/15 is the run as executed.

## A dataset ambiguity, found by the model

T1 asks for revenue for the period ending 2007-09-29. The archive holds **two**
observations for that exact concept and period:

```
us-gaap:SalesRevenueNet   24,006,000,000   2006-10-01 → 2007-09-29
us-gaap:SalesRevenueNet   24,578,000,000   2006-10-01 → 2007-09-29
```

This is the 2.5 dimension-member limitation: the company-concept endpoint
aggregates facts that differ only by dimension, and the member is not in the
payload. The model retrieved the *second*; the dataset's expectation is the
first, chosen by `ORDER BY period_end LIMIT 1`. **The dataset's expected value
for T1 is arbitrary**, and the failure is recorded as B when D is correct.

The scripted targets could never have found this: their answers were fixed, so
which of the two values existed never mattered. This is the clearest argument
for the experiment existing at all.

## What is *not* concluded

- **No data defect.** The archive was correct in every case examined. Nothing
  here justifies changing ingestion, the registry, or the archive.
- **A B is not a reason to change ST-EVA.** 31 of 31 recorded failures are the
  model's.
- **This is one model at one temperature.** It does not generalise to "LLMs",
  and the two-pass comparison has not been run.

## The one change made mid-run

After the first smoke test, the system prompt was corrected to state that the
`status` filter matches `status.validation_status` and not the evidence state.
That is a harness fix for a mis-wiring I introduced — I had taught the model an
evidence-state vocabulary without saying which parameter accepted it. The
scoring rules, dataset, tools and auditor were untouched, and the correction
did not eliminate the mistake (T13 still made it).

## Next

1. **Decide A1 and A2.** A1 is the one that matters: a silent empty list is
   indistinguishable from an absent fact, and it produced 7 of 15 false
   negatives. The fix is small and belongs in the query surface — but it is
   sealed, so it is a decision, not a patch.
2. **Fix the two C-class false passes** before the second model, or the second
   run inherits an auditor that rewards returning nothing.
3. **Make T1's expectation deterministic** — assert that both values are
   acceptable, or mark the test D.
4. **Then run models B, C, D** against the identical dataset, snapshot, tools
   and auditor. Only the target changes.
